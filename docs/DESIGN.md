# rescade: дизайн и принятые решения

Сервис-надстройка над restic: запускает по расписанию каскады команд (backup, retain, prune, check, copy, run),
хранит состояние и историю запусков. Конфиги в YAML. Стек: restic, Node.js, TypeScript.

## Архитектура

- **Сервис (демон) владеет всем состоянием**: расписанием, исполнением, историей. CLI и веб-интерфейс — тонкие клиенты.
- Клиенты умеют только: запустить каскад, остановить запуск, посмотреть состояние, запросить лог по требованию.
- Конфиг только в YAML (источник правды). Клиенты его не меняют. Веб-редактор возможен позже как отдельный слой,
  который пишет файл и просит сервис перечитать конфиг (SIGHUP или `POST /api/reload`).
- Ядро (`core`) — библиотека без сети. Демон — обёртка над ней. Должен работать `run --local` без демона (отладка, аварии).
- Веб-интерфейс — статика поверх API, необязателен. Собирается вместе с демоном, демон отдаёт его сам
  (путь к сборке находит относительно себя, без настройки). Позже возможна опция отдавать его через nginx.

## Пакеты (монорепо, pnpm workspaces)

- `core`: загрузчик конфигов, адаптер restic, исполнитель каскадов, мьютексы репо, планировщик, хранилище, шина событий
- `daemon`: бинарник `rescaded`, связывает core с HTTP API, обрабатывает SIGTERM/SIGHUP, ранний прогрев репо при старте
- `cli`: бинарник `rescade` (подкоманды), клиент API; `validate` работает локально через core
- `web`: веб-интерфейс (React, TanStack Query, Tailwind 4, Vite), статика, которую отдаёт демон

Библиотеки: `yaml` (позиции узлов), `zod` (схема), `croner` (cron), встроенный `node:sqlite` (Node >= 26),
Fastify (+ `@fastify/swagger`: OpenAPI по схемам маршрутов, `@fastify/swagger-ui`, `@fastify/static` для веб-интерфейса),
`pino`. Логи демона в JSON (stdout). Экран логов демона в веб-интерфейсе отложен, источник для него ещё не выбран.

## Конфиг

- Каталог `config/*.yaml` (или один файл), путь через `--config-dir` / `RESCADE_CONFIG_DIR`.
- Каждый файл разбирается отдельно, записи `repos`/`sets`/`cascades` сливаются по имени. Дубль имени = ошибка.
  Якоря между файлами не работают (осознанно).
- Неизвестные ключи = ошибка (строгая валидация).
- `${VAR}`, `${VAR:-default}`, `$$` — подстановка из env в значениях. Секреты только через env демона.
- Репозитории задаются явным списком (пути и имена могут быть разными).
- `retention` лежит в репо. Шаг `retain` = `restic forget` по политике репо, без `--prune`. Шаг `prune` отдельный.
- `from:` у репо = «создан из этого» (`restic init --from-repo --copy-chunker-params`).
- Расписание внутри каскада (`schedule`: cron-строка или список), без расписания = только ручной запуск.
- `on-busy: skip | wait` (+ `wait-timeout`) на каскад. По умолчанию `skip`.
- `group` у репо и каскада: только для показа, в веб-интерфейсе сворачиваемый заголовок на месте первого члена
  группы (порядок конфига сохраняется); без `group` запись показывается отдельно, как раньше.
- Бэкенды restic (local, sftp, rest, s3, swift, b2, azure, gs, rclone) без специального кода: ключи и токены
  в `env` репо (значения через `${VAR}` из окружения демона, файлы путями), опции бэкенда в `options`.
  `validate` проверяет префикс `path` (неизвестный = ошибка; restic отверг бы его только при запуске), опции
  против бэкенда репо (чужой бэкенд = ошибка, неизвестное имя своего = предупреждение), `RESTIC_REPOSITORY*`/`RESTIC_PASSWORD*`
  в `env` (ошибка) и пары `copy`/`from`: restic один на оба репо, ключи бэкенда и `-o` общие, поэтому разные значения
  одного имени на одном бэкенде = ошибка. Подробно по бэкендам: `docs/backends.md`.
- Шаг `run`: `command` массивом argv (без shell), `shell: true` + строка по явному флагу, `env`, `cwd`,
  `timeout` (по умолчанию 1 час), `lock: [repo, ...]`.

## Исполнение

- Мьютекс на репозиторий; шаг берёт мьютексы всех репо, которые трогает (`backup`/`retain`/`prune`/`check` свой, `copy` оба,
  `run` свой `lock`), все сразу или ни одного (без взаимоблокировок). Ожидающие обслуживаются по очереди: свободный репо
  не отдаётся позднему запросу, если его ждёт более ранний. Шаги и каскады с разными репо идут параллельно.
  Блокировка на шаг, не на каскад.
- `on-busy` проверяется на каждом шаге, для репо этого шага. `skip`: шаг и остальные шаги `skipped`, запуск `skipped` с причиной
  (уже выполненные шаги остаются как есть). `wait`: шаг ждёт, запуск `queued` с причиной; `wait-timeout` действует на каждое
  ожидание шага, без него ждём без ограничений; истёк = как `skip`. Отмена снимает и ожидающий запуск.
- Каскад не запускается, пока идёт его предыдущий запуск (независимо от `on-busy` и триггера): новый запуск записывается
  как `skipped` с причиной. Если в один момент срабатывают несколько выражений `schedule`, это один запуск.
- Ошибка шага: каскад останавливается, статус `failed` с причиной (код выхода, хвост stderr), остальные шаги `skipped`.
- `backup` с кодом 3 (часть файлов не прочитана) = `warning`, каскад идёт дальше.
- Пропущенные запуски не догоняем (нет `catch-up`).
- Статусы: `queued`, `running`, `success`, `warning`, `failed`, `cancelled`, `skipped`, `interrupted`.
- Отмена: SIGTERM дочернему restic, таймаут (~30 с), потом SIGKILL. При остановке демона: прекратить планирование,
  переслать SIGTERM детям, пометить активные запуски `interrupted`. Stale-lock'и не снимаем автоматически, показываем в статусе.
- Локи restic: после успешного `cat config` в ensure (перед каждым шагом внутри мьютекса, то есть когда наших restic на репо
  нет, и при прогреве) `restic list locks --no-lock` и `restic cat lock --no-lock <id>` для первых 10. Лок `stale`, если
  старше 30 минут (порог самого restic; живой restic обновляет лок раз в 5 минут). Проверку «тот же хост, процесса нет»
  не делаем. Ошибка чтения локов шаг не проваливает, а показывается в состоянии репо. Сразу после `init` локи не читаются.
- restic запускается через `spawn` без shell; секреты через env процесса, не через аргументы; разбор `--json`.
- Для `run`-шагов в дочерний процесс передаётся только заданное в шаге окружение, не всё окружение демона
  (без `PATH` программа ищется в системном пути по умолчанию). `shell: true` = `/bin/sh -c`.
- restic получает окружение демона без `RESTIC_REPOSITORY*`/`RESTIC_PASSWORD*` (и `FROM_`-вариантов), поверх него `env`
  репо (для `copy` сначала источника, потом цели); `options` репо идут как `-o key=value`. Источник для `copy` и
  `init --copy-chunker-params` передаётся через `RESTIC_FROM_REPOSITORY`/`RESTIC_FROM_PASSWORD`.
- Требуется restic >= 0.17 (коды выхода 10 и 12). Любой другой ненулевой код `cat config` = `unreachable`.
  `rescaded` при старте и `rescade run --local` перед запуском читают `restic version`: старше 0.17, не запустился
  или версия не разобралась = предупреждение (в лог демона, в stderr CLI), не ошибка.
- `cat config` ограничен таймаутом (`RESCADE_REPO_CHECK_TIMEOUT`, по умолчанию 2m): недоступный REST/S3 restic
  ретраит минутами. Истёк = `unreachable`, init не делается. У backup/prune/copy/check таймаута нет.
- Коды выхода `rescade run`: 0 success, 3 warning, 1 failed или interrupted, 130 cancelled, 75 skipped (репо заняты или
  каскад уже идёт; только через демон), 2 ошибка использования. Остальные команды клиента: 0, 1 ошибка демона или нет связи, 2.

## Инициализация репозиториев и сверка параметров

- Автоинициализация, отдельной команды `init` нет. Перед каждым шагом (внутри мьютекса репо): `restic cat config`.
  Код 10 (репо не существует) → `init` (с `--from-repo` и `--copy-chunker-params`, если задано `from`; источник проверяется первым).
  Неверный пароль или провал `init` → шаг `failed`. Недоступный хост → `unreachable`, `init` не делаем никогда.
- При старте тот же проход как ранний прогрев. Ошибки конфигурации и ошибки на достижимых репо останавливают сервис.
  Во время работы ошибка ensure/init только проваливает шаг.
- Проверка монтирования вне зоны сервиса (в systemd: `RequiresMountsFor=`).
- Сверка `chunker_polynomial` (из `restic cat config`) при старте по рёбрам `from` и перед каждым `copy`.
  Без кеша: репо могли пересоздать вручную. Расхождение = `warning` на шаге, каскад идёт дальше.
  Пересоздание с теми же параметрами не считается ошибкой.

## API и настройки сервиса

- TCP (не Unix-сокет), по умолчанию `127.0.0.1:8765`. Токен обязателен всегда (`Authorization: Bearer`, сравнение за постоянное время).
  Токен через env или файл (права 600), не через аргументы. Без токена демон не стартует и подсказывает, как его создать
  (сам не генерирует).
- Проверка `Host` включается `RESCADE_ALLOWED_HOSTS` (через запятую): `host:port` пускает только на этом порту, `host` на
  любом, в том числе без порта в заголовке (прокси на 80/443). Всегда разрешены `localhost`, `127.0.0.1`, `[::1]` и хост
  из `RESCADE_ADDR` с портом демона. Иначе 403. Без переменной или с пустой пускаются все: доступ к данным и управлению
  всё равно только по токену в `Authorization`, который браузер сам не подставит, а без токена отдаются только
  статика, `/api/health` и описание API.
- CORS только для origin из `RESCADE_CORS_ORIGINS` (по умолчанию никого). Preflight `OPTIONS` от разрешённого origin
  проходит без токена.
- Настройки сервиса через env/флаги, не YAML: `RESCADE_ADDR`, `RESCADE_URL`, `RESCADE_TOKEN_FILE`, `RESCADE_TOKEN`,
  `RESCADE_CONFIG_DIR`, `RESCADE_DATA_DIR` (по умолчанию `/var/lib/rescade`, база `rescade.db`),
  `RESCADE_HISTORY_RETENTION` / `RESCADE_LOG_RETENTION` (срок хранения истории и логов),
  путь к restic (`RESCADE_RESTIC`), таймаут проверки репо (`RESCADE_REPO_CHECK_TIMEOUT`), `RESCADE_LOG_LEVEL`,
  `RESCADE_PUBLIC_URL` (адрес веб-интерфейса снаружи, для ссылок в уведомлениях).
- Клиент ищет токен: `--token-file`, `RESCADE_TOKEN`, `RESCADE_TOKEN_FILE`, `~/.config/rescade/token`. Сервер: `--token-file`,
  `RESCADE_TOKEN`, `RESCADE_TOKEN_FILE`, `/etc/rescade/token`. Предупреждение, если права на файл слишком широкие.
- API под префиксом `/api`, остальные пути принадлежат веб-интерфейсу: файлы сборки, а для путей без расширения
  `index.html` (страницы маршрутизируются в браузере). Статика отдаётся без токена, но за проверкой `Host`;
  неизвестный путь под `/api` даёт JSON-ошибку, а не страницу.
- Эндпоинты: `GET /api/status`, `GET /api/cascades`, `GET /api/runs`, `GET /api/runs/:id`, `GET /api/runs/:id/log?step=&after=`,
  `POST /api/cascades/:name/run`, `POST /api/runs/:id/cancel`, `POST /api/runs/:id/rerun`, `GET /api/repos`, `GET /api/repos/:name/snapshots`,
  `GET /api/repos/:name/snapshots/:id/ls?path=`, `POST /api/repos/:name/snapshots/:id/restore`, `GET /api/events` (SSE),
  `POST /api/reload`, `POST /api/notifications/:name/test`, `GET /api/openapi.json`, Swagger UI на `/api/docs`. Перезагрузка конфига по SIGHUP или
  `POST /api/reload`; ошибка в новом конфиге оставляет старый. Запуски, уже идущие, доживают со старым конфигом.
  Перезагрузки идут по одной (вторая ждёт первую), иначе два чтения, закончившись не по порядку, оставили бы старый.
- `POST /api/reload` отвечает, когда конфиг прочитан: 200 с `{ at, ok, errors }` и при ошибках в конфиге (это итог
  перезагрузки, а не ошибка запроса; тот же объект попадает в `config.lastReload` статуса), 503 при остановке.
  CLI `rescade reload` (код 1 и ошибки в stderr, если конфиг битый), в вебе кнопка Reload config в шапке.
- `GET /api/status`: версия, время старта демона, путь к конфигу, время загрузки действующего конфига и итог последней
  перезагрузки (`ok`, ошибки `файл:строка:колонка`). Так клиенты видят, что SIGHUP с битым конфигом не применился.
- `GET /api/events`: события `run`, `step`, `log`, `repo`. Фильтры `?run=<id>` и `?cascade=<name>` (тогда без `repo`).
- У строки лога есть `id` (rowid в SQLite, растёт по всем запускам), он же в событии `log`. Чтобы следить за идущим
  запуском без потерь и дублей: подписаться на `?run=`, потом запросить лог, события с `id` не больше последней
  полученной строки отбросить. После обрыва SSE лог догоняется через `?after=<id>`.
  `rescade run` сначала подписывается на `?cascade=`, потом делает POST: так не теряются события, пришедшие раньше ответа.
- `GET /api/openapi.json` (OpenAPI 3.1) и Swagger UI (`/api/docs/*`) отдаются без токена (секретов в них нет, а браузер
  не пошлёт `Authorization` при открытии страницы; при необходимости закрываются обратным прокси), проверка `Host`
  остаётся. Токен для «Try it out» вводится через Authorize. Схемы ответов (`packages/daemon/src/schemas.ts`) заданы у каждого
  маршрута: по ним Fastify сериализует ответы, они же становятся компонентами документа.
  Копия документа лежит в `docs/openapi.json`, тест следит, чтобы она совпадала с отдаваемой.
- Ошибки API: `{ "error": "..." }`; 400 неверные параметры, 401 токен, 403 `Host`, 404, 409 отмена незапущенного
  (у снапшотов: эксклюзивный лок не ушёл за время ожидания), 502 restic упал, 503 демон останавливается, 504 репо
  не ответил за таймаут проверки. Пароли в URL репо (`rest:https://user:pass@...`) в `GET /api/repos` скрываются.
- При SIGTERM: стоп планировщика, отмена запусков (SIGTERM детям), они и их шаги получают `interrupted`, потом закрытие API.
  При старте запуски, оставшиеся `running`/`queued` после падения, помечаются `interrupted`. Второй сигнал завершает сразу.
- Модель данных: run (id, каскад, триггер, статус, времена, причина), step (индекс, тип, статус, код выхода,
  длительность, summary, у backup ещё репо, куда ушёл снапшот), log (строки по шагам с id, отдельно от метаданных для ротации). SQLite (`node:sqlite`, WAL,
  версия схемы в `user_version`). Состояние репо и мьютексы в памяти.
- Срок хранения: завершённые запуски старше `RESCADE_HISTORY_RETENTION` (по умолчанию `180d`) удаляются вместе с шагами
  и логом, у запусков старше `RESCADE_LOG_RETENTION` (по умолчанию `30d`) удаляются только строки лога (`stderrTail`
  остаётся в шаге). `0` = без ограничения. Последний запуск каждого каскада и идущие запуски не удаляются никогда.
  Чистка при старте демона и раз в час. Логи самого демона пишутся в stdout, их ротирует journald.
- Уведомления: см. раздел «Уведомления».

## Уведомления

- Секция `notifications` в YAML (сливается по имени, как остальные; перечитывается при reload). Пока один тип,
  `type: telegram` (поле обязательно, чтобы другие типы добавлялись без поломки): `token` (через `${VAR}`), `chat`
  (id числом или строкой, `@channel`), `thread` (тема в группе, `message_thread_id`), `events`, `cascades`.
- События: `failed`, `interrupted`, `warning`, `recovered`, `reload-failed`, `repo-problem` (это набор по умолчанию),
  по явному выбору ещё `skipped`, `cancelled`, `success`. `cascades` ограничивает запуски этими каскадами, а события
  репо и restore теми репо, которые эти каскады трогают (`stepRepos`). `reload-failed` фильтру не подчиняется.
- Запуск: сообщение, когда запуск закончился со статусом из `events`, при любом триггере. `recovered` = первый
  `success`/`warning` каскада после `failed`/`interrupted` (`Store.previousOutcome`, `skipped`/`cancelled` между ними
  не считаются); у такого запуска одно сообщение, о восстановлении, даже если его статус тоже в `events`.
  Запуски, помеченные `interrupted` при старте после падения, тоже уходят в уведомления.
- Restore (запускается руками) уведомляет только о `failed`/`interrupted`.
- `repo-problem`: переход репо из ok или «ещё не проверялся» в любую проблему (кроме `cancelled`), обратно = `recovered`.
  Состояние в памяти уведомителя, повторные проверки перед шагами не спамят; после перезапуска демона о плохом репо
  сообщается снова (при прогреве).
- `reload-failed`: каждая неудачная перезагрузка, в сообщении первые 5 ошибок; следующая удачная = `recovered`.
- Сообщение HTML (`parse_mode`), подставляемое экранируется: значок, каскад и статус, причина (обрезается до 1500
  символов), триггер, длительность, имя хоста (`os.hostname()`, чтобы несколько демонов могли писать в один чат),
  ссылка `<RESCADE_PUBLIC_URL>/runs/<id>` (или `/repos/<name>`), если задан `RESCADE_PUBLIC_URL`.
- Отправка в демоне (`packages/daemon/src/notify.ts`, `fetch` к Bot API; ядро без сети). Очередь на каждое
  уведомление, порядок внутри неё сохраняется; исполнение не ждёт отправку. Таймаут 10 с; повтор при сетевой ошибке,
  5xx и 429 (по `retry_after`), всего 3 попытки, потом ошибка в лог и сообщение выбрасывается; 4xx не повторяется.
  Токен стоит в URL, поэтому в ошибки и лог URL не попадает. При остановке демон ждёт очереди до 5 с (чтобы ушли
  `interrupted` от самой остановки), остальное выбрасывает.
- Проверка: `validate` в сеть не ходит (схема, ссылки на каскады, формат токена = предупреждение);
  `POST /api/notifications/:name/test` и `rescade notify-test <name>` шлют пробное сообщение один раз, без повторов,
  ошибка Telegram возвращается как есть (502).
- Не сделано: ошибка последней доставки в статусе и вебе.

## Просмотр снапшотов

- `GET /api/repos/:name/snapshots`: `restic snapshots --json`, новые сверху: id, время, хост, пользователь, пути, теги,
  родитель и из `summary` (restic 0.17+) размер (`total_bytes_processed`), число файлов, `data_added`.
- `GET /api/repos/:name/snapshots/:id/ls?path=`: `restic ls --json <id> <path>`, только то, что прямо в каталоге
  (restic читает деревья по пути, не всё дерево). Каталог без `path` = `/`. id только hex от 8 символов, путь
  абсолютный (иначе 400). Для файла ответ содержит его самого. Отсутствующий путь restic не считает ошибкой (пустой
  вывод, код 0), поэтому 404 даём сами, если в выводе нет узла самого каталога (у `/` его нет никогда). Больше 10 000
  записей обрезается с `truncated: true`.
- Блокировки: мьютекс rescade не берётся, иначе просмотр ждал бы часовой backup. restic сам ставит неэксклюзивный лок,
  он уживается с backup; против эксклюзивного лока prune `--retry-lock 10s`, потом 409. Таймаут вызова тот же, что
  у проверки репо (`RESCADE_REPO_CHECK_TIMEOUT`), иначе недоступный REST/S3 держал бы запрос минутами (504).
  Если клиент ушёл, restic получает SIGTERM.
- Безопасность (принято): имена файлов, размеры и времена из бэкапов видны любому, у кого есть токен. Отдельной роли
  «только запуск» нет; токен и так даёт управление каскадами. Содержимое файлов API не отдаёт.
- Ссылка из запуска: шаг backup хранит репо (`StepRecord.repo`, схема базы версии 2, миграция с 1), `summary.snapshot_id`
  на странице запуска ведёт на снапшот. У старых запусков репо нет, ссылки тоже.
- Владелец в записи `ls` только числом (`uid`, `gid`): имена restic хранит в дереве, но `ls --json` их не выводит,
  а переводить числа в имена на стороне демона нельзя (в контейнере свой `/etc/passwd`). Симлинк = `type: "symlink"`,
  цель ссылки `ls` не показывает.
- Клиенты: `rescade snapshots <repo>`, `rescade ls <repo> <id> [path]` (каталоги первыми, владелец `uid:gid`); в веб-интерфейсе
  страница репо `/repos/:name` (ссылка с имени на `/repos`: состояние, id, полином, локи и список снапшотов) и `/repos/:name/snapshots/:id`:
  файлы деревом (`@headless-tree`), свёрнутым; каталог запрашивается через `ls`, когда его раскрывают. Колонки: имя,
  симлинк (иконка), права, `uid:gid`, размер (у каталогов нет), время изменения. Иконки из Material Design Icons
  (`@mdi/js`): чекбоксы `checkbox-blank-outline` / `checkbox-outline` / `minus-box-outline`, пока каталог грузится,
  на месте его чекбокса крутится `loading`; раскрытие (и у групп, и у шагов каскада) `chevron-right` с поворотом.
  Ответ `ls` для пары снапшот+путь не меняется и в кеше не устаревает; список снапшотов перезапрашивается после
  каждого завершённого шага.

## Восстановление

- Каталог для восстановления задаёт только демон: `--restore-dir` / `RESCADE_RESTORE_DIR`. Из CLI и веба его указать
  нельзя. Не задан = restore выключен (API 409 с подсказкой). Нет каталога = демон создаёт его (с родителями, права 700:
  восстановленные файлы бывают секретами); не смог создать или на этом месте не каталог = демон не стартует.
  Существующий и непустой каталог годится.
- Снапшот восстанавливается в `<restore-dir>/<короткий id>` (первые 8 hex) с полными путями из снапшота, префикс `/host`
  не снимается: `/restore/c8b33f97/host/etc/samba/smb.conf`. Повторное восстановление того же снапшота идёт в тот же
  каталог: restic докладывает недостающее и перезаписывает изменённое (по умолчанию `--overwrite always`, ничего
  не удаляет).
- Целиком или выбранные пути (абсолютные; каталог берётся с поддеревом) через `--include`. Спецсимволы шаблонов
  restic (`*?[]\`) экранируются обратной косой чертой; `!` отрицает шаблон только в его начале, а там у абсолютного
  пути `/`; `$VAR` в аргументах restic не раскрывает (проверено на 0.19.1). `/` среди путей = весь снапшот. Отсутствующий путь restic ошибкой не считает (код 0, ничего не восстановлено), поэтому
  `files_restored` = 0 при заданных путях даёт `failed`.
- Это запуск в истории: `RunRecord` без `cascade`, с полем `restore` (`repo`, `snapshot`, `paths`, `target`), триггер
  `manual`, один шаг типа `restore` с `repo`. Лог, SSE, отмена, `interrupted` при остановке и срок хранения общие
  с каскадами. Схема базы v3: `runs.restore` (JSON), `cascade` у restore пустая строка в базе.
- Блокировки: restore берёт мьютекс репо, как шаг, и ждёт его без ограничения. Пока он идёт, ждут и prune, и backup
  (каскад с `on-busy: skip` пропускается с причиной «held by run N (restore)»). Перед restore `restic cat config`
  без init: отсутствующий репо = `failed`.
- `restic restore --json`: прогресс отбрасывается, ошибки (`error`, `exit_error`) переводятся в текст, `summary`
  сохраняется в шаге. Код 1 (в том числе «There were N errors») = `failed`. Неизвестный снапшот = `failed`.
- API: `POST /api/repos/:name/snapshots/:id/restore` с `{ "paths"?: string[] }` (до 1000 абсолютных путей), ответ 202
  с записью запуска, дальше как у каскада (`/api/runs/:id`, лог, отмена). Тело можно не слать (весь снапшот);
  лишние поля, в том числе `target`, Fastify отбрасывает. CLI: `rescade restore <repo> <id> [path...]`
  подписывается на все события до POST и отбирает свои по id запуска; по умолчанию ждёт и показывает лог,
  `--detach` сразу печатает id; коды выхода как у `run`, кроме 75 (restore не пропускается, а ждёт).
- В Docker: отдельный том или bind mount с записью, `RESCADE_RESTORE_DIR=/restore`.
- Веб: у каждой записи дерева чекбокс, по умолчанию ничего не выбрано. Хранятся только верхние выбранные пути:
  отмеченный каталог уходит в запрос один, без детей. Каталог, у которого отмечены все записи, становится отмеченным
  сам (кроме обрезанного списка в 10 000). Снятие отметки внутри отмеченного каталога заменяет его остальными
  записями на каждом уровне вниз; у обрезанного каталога так нельзя, и чекбоксы внутри него неактивны. Встроенные чекбоксы
  headless-tree не годятся: при отметке каталога они грузят всё поддерево. Под деревом, когда что-то выбрано,
  кнопка Restore и путь `<restore-dir>/<короткий id>`: каталог демон отдаёт в `GET /api/status` (`restoreDir`, нет поля =
  restore выключен, кнопка неактивна с подсказкой). После запуска открывается страница запуска.

## Повтор с проваленного шага

- Повторить можно запуск каскада (не restore) со статусом `failed`, `cancelled`, `interrupted` или `skipped`, если у него
  есть шаги (`skipped` без шагов = каскад уже шёл, повторять нечего). Идущий запуск повторить нельзя.
- Повтор = новый запуск, старый не меняется. В `RunRecord` поля `rerunOf` (id исходного) и `fromStep`; триггер `manual`.
  Схема базы v4: `runs.rerun_of`, `runs.from_step`.
- `fromStep` = первый шаг исходного запуска, который не закончился `success`/`warning` (нет записи шага = не выполнен:
  после `kill -9` записи бывают не у всех шагов). Повтор с произвольного шага не делаем.
- Шаги до `fromStep` в новом запуске не записываются вовсе (не `skipped`: `skipped` с причиной делает весь запуск
  `skipped`), индексы шагов совпадают с индексами в конфиге. Статус нового запуска считается только по его шагам.
- Конфиг мог смениться (SIGHUP): метки (`describeStep`) шагов `0..fromStep-1` исходного запуска сверяются с текущим
  каскадом, расхождение или удалённый каскад = отказ. Проваленный шаг и следующие не сверяются: обычно их как раз
  исправили в конфиге.
- Остальное как у обычного запуска: каскад уже идёт = запись `skipped` с причиной, `on-busy` и мьютексы по текущему
  конфигу. Повтор старого запуска при более новом успешном не запрещается: шаги restic можно повторять.
- API: `POST /api/runs/:id/rerun`, 202 с новым запуском; 404 нет запуска, 409 повторить нельзя (с причиной), 503 демон
  останавливается. CLI: `rescade rerun <run-id> [--detach]`, вывод и коды выхода как у `run`.
- Веб: кнопка Rerun from failed только на странице запуска, который можно повторить; после нажатия открывается
  новый запуск. У повтора ссылка на исходный запуск и строка о шагах, выполненных в нём.

## Docker

- Один образ: `rescaded` (точка входа), `rescade` (для `docker exec`), собранный веб-интерфейс и restic.
  Многоступенчатая сборка: pnpm-сборка, затем только prod-зависимости (`pnpm deploy --prod`) на `node:26-alpine`.
- restic берётся бинарником с GitHub-релиза фиксированной версии со сверкой SHA-256 (в пакетах дистрибутивов
  бывает старше 0.17). В образе также `openssh-client` (sftp, с `StrictHostKeyChecking accept-new` и
  `known_hosts` в `/var/lib/rescade`), `ca-certificates`, `tzdata`; `rclone` не входит.
- PID 1 — `tini`: демон убивает группы процессов, но осиротевших внуков кто-то должен пожинать.
- Процесс работает от root: restic должен читать любые файлы источников. Источники монтируются только для чтения.
- Внутри контейнера `RESCADE_ADDR=0.0.0.0:8765`, `RESCADE_CONFIG_DIR=/etc/rescade/config` (только чтение),
  `RESCADE_DATA_DIR=/var/lib/rescade` (том), `RESTIC_CACHE_DIR=/var/lib/rescade/cache` (кеш restic переживает
  пересоздание контейнера), токен файлом через Docker secret (`RESCADE_TOKEN_FILE=/run/secrets/rescade_token`).
- `GET /api/health` без токена (за проверкой `Host`): 200 `{ "ok": true }`, ничего о состоянии не раскрывает;
  его опрашивает `HEALTHCHECK` образа.
- SIGHUP: `docker kill -s HUP <контейнер>`; SIGTERM от `docker stop` с `stop_grace_period` больше таймаута
  SIGTERM→SIGKILL у restic.
- Имя хоста в снапшотах фиксируется через `hostname:` в compose: без `--host` restic пишет в снапшот имя системы,
  а у контейнера оно иначе меняется при пересоздании (и родительский снапшот, который ищется по `host,paths`,
  не находится). `RESTIC_HOST` не годится: restic берёт его ещё и фильтром по умолчанию в `forget`, `copy`,
  `check`, `snapshots`, и `retain`/`copy` молча стали бы касаться только снапшотов этого хоста.
- Куда монтировать источники, решает пользователь. Документация и пример предупреждают: путь внутри контейнера
  не должен пересекаться с путями образа (`/etc`, `/usr`, `/var/lib/rescade` и т. п.) и должен оставаться
  постоянным (restic ищет родительский снапшот по `host,paths`; подменить пути в снапшоте restic не умеет,
  restic#2714). Предлагается префикс `/host` (`/home:/host/home:ro`, в `sets` пути `/host/...`). Цена префикса:
  снапшоты, снятые без него, родителями не станут (первый backup после переезда читает всё), при восстановлении
  префикс снимается через `restic restore <id>:/host/home --target /home`. Монтировать по хостовым путям тоже
  можно, если они ни с чем в образе не пересекаются.
- Порт публикуется на `127.0.0.1:8765`; `RESCADE_ALLOWED_HOSTS` по желанию ограничивает имена, под которыми он доступен.
- Публикация: GitHub Actions, `ghcr.io/artss/rescade`, `linux/amd64` и `linux/arm64` через buildx;
  каждый пуш в `main` — релиз: образ `X.Y.Z`, `X.Y`, `latest` и тег `vX.Y.Z`. Перед сборкой образа гоняются тесты.
- Версия одна на весь монорепо и живёт только в git-тегах: в `package.json` всех пакетов `0.0.0-dev`, в репо CI
  ничего не коммитит. Следующую версию считает `scripts/version.mjs next` от последнего тега по conventional commits
  после него: breaking поднимает major (до 1.0 — minor), `feat` — minor, остальное — patch; без тегов `0.1.0`.
  `Dockerfile` получает её через `ARG VERSION` и вписывает во все `package.json` до сборки. Тег ставится после
  успешной публикации образа; прогоны релиза идут по одному (`concurrency`). Версию показывают `rescade --version`,
  `GET /api/status` и `info.version` в OpenAPI (`rescade status` предупреждает, если версии CLI и демона разные)
  и шапка веб-интерфейса.
- Пример в `examples/docker-compose.yaml` рядом с `examples/config`.

## Веб-интерфейс

- React + TanStack Query, Tailwind 4 (`@tailwindcss/vite`), сборка Vite; язык интерфейса английский.
  Типы ответов через `import type` из `@rescade/core`, ядро в бандл не попадает.
- Экраны: каскады (последний и следующий запуск, идущий запуск, Run), история (фильтр по каскаду, страницы по 50 через
  `offset`, номер страницы в URL, общее число в заголовке `X-Total-Count`), запуск (шаги, summary, `stderrTail`, живой лог, Cancel), репозитории (состояние, `lockedBy`, локи restic),
  снапшоты репо и браузер каталогов снапшота,
  состояние демона и конфига из `/api/status`. Позже экран логов демона.
- Токен вводится на странице и хранится в `sessionStorage` (в `localStorage` по «запомнить»), в URL не попадает.
  `EventSource` не умеет слать заголовки, поэтому SSE читается через `fetch` со стримом.
- Одна подписка на `/api/events` на всё приложение (одно соединение на вкладку: у браузера лимит соединений на origin)
  обновляет кеш запросов: запуск и его шаги через `setQueryData`, списки через `invalidateQueries`. Строки лога
  попадают в кеш только для открытого лога и склеиваются с ответом `GET .../log` по `id`, поэтому порядок «подписка,
  потом запрос» соблюдается сам. На каждом (пере)подключении всё перезапрашивается, лог через `after`, если он уже
  был получен целиком. `/api/status` опрашивается раз в 30 с: у перезагрузки конфига нет события.
- Маршрутизация в браузере (`wouter`): `/`, `/runs?cascade=`, `/runs/:id`, `/repos`, `/repos/:name`,
  `/repos/:name/snapshots/:id?path=`. `pnpm dev` в `packages/web`
  проксирует `/api` на демон (`RESCADE_URL`).
- Тесты: логика (SSE-парсер, разбор событий в кеш, склейка лога); компоненты через `@testing-library/react`
  и happy-dom на настоящем демоне (`startDaemon`, SQLite во временном каталоге, фейковый restic), поднятом
  в `globalSetup`. Адрес happy-dom равен адресу демона: origin общий, как в бою.
