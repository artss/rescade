# rescade: дизайн и принятые решения

Сервис-надстройка над restic: запускает по расписанию каскады команд (backup, retain, prune, check, copy, run),
хранит состояние и историю запусков. Конфиги в YAML. Стек: restic, Node.js, TypeScript.

## Архитектура

- **Сервис (демон) владеет всем состоянием**: расписанием, исполнением, историей. CLI и веб-интерфейс — тонкие клиенты.
- Клиенты умеют только: запустить каскад, остановить запуск, посмотреть состояние, запросить лог по требованию.
- Конфиг только в YAML (источник правды). Клиенты его не меняют. Веб-редактор возможен позже как отдельный слой,
  который пишет файл и просит сервис перечитать конфиг (SIGHUP).
- Ядро (`core`) — библиотека без сети. Демон — обёртка над ней. Должен работать `run --local` без демона (отладка, аварии).
- Веб-интерфейс отдельно от сервиса (статика поверх API), необязателен.

## Пакеты (монорепо, pnpm workspaces)

- `core`: загрузчик конфигов, адаптер restic, исполнитель каскадов, мьютексы репо, планировщик, хранилище, шина событий
- `daemon`: связывает core с HTTP API, обрабатывает SIGTERM/SIGHUP, ранний прогрев репо при старте
- `cli`: бинарник `rescade` (подкоманды), клиент API; `validate` работает локально через core
- `web`: позже

Библиотеки: `yaml` (позиции узлов), `zod` (схема), `croner` (cron), встроенный `node:sqlite` (Node >= 22.13),
`pino`, лёгкий HTTP (Fastify или `http` + SSE).

## Конфиг

- Каталог `config/*.yaml` (или один файл), путь через `--config-dir` / `RESCADE_CONFIG_DIR`.
- Каждый файл разбирается отдельно, записи `repos`/`sets`/`cascades` сливаются по имени. Дубль имени = ошибка.
  Якоря между файлами не работают (осознанно).
- Неизвестные ключи = ошибка (строгая валидация).
- `${VAR}`, `${VAR:-default}`, `$$` — подстановка из env в значениях. Секреты только через env демона.
- Репозитории задаются явным списком (пути и имена могут быть разными).
- `retention` лежит в репо. Шаг `retain` = `restic forget` по политике репо, без `--prune`. Шаг `prune` отдельный.
- `from:` у репо = «создан из этого» (`restic init --from-repo --copy-chunker-params`).
- Расписание внутри каскада (`schedule`: cron-строка или список), без расписания = только ручной запуск.
- `on-busy: skip | wait` (+ `wait-timeout`) на каскад. По умолчанию `skip`.
- Шаг `run`: `command` массивом argv (без shell), `shell: true` + строка по явному флагу, `env`, `cwd`,
  `timeout` (по умолчанию 1 час), `lock: [repo, ...]`.

## Исполнение

- Мьютекс на репозиторий; шаг берёт мьютексы всех репо, которые трогает (`backup`/`retain`/`prune`/`check` свой, `copy` оба,
  `run` свой `lock`), все сразу или ни одного (без взаимоблокировок). Ожидающие обслуживаются по очереди: свободный репо
  не отдаётся позднему запросу, если его ждёт более ранний. Шаги и каскады с разными репо идут параллельно.
  Блокировка на шаг, не на каскад.
- `on-busy` проверяется на каждом шаге, для репо этого шага. `skip`: шаг и остальные шаги `skipped`, запуск `skipped` с причиной
  (уже выполненные шаги остаются как есть). `wait`: шаг ждёт, запуск `queued` с причиной; `wait-timeout` действует на каждое
  ожидание шага, без него ждём без ограничений; истёк = как `skip`. Отмена снимает и ожидающий запуск.
- Каскад не запускается, пока идёт его предыдущий запуск (независимо от `on-busy` и триггера): новый запуск записывается
  как `skipped` с причиной. Если в один момент срабатывают несколько выражений `schedule`, это один запуск.
- Ошибка шага: каскад останавливается, статус `failed` с причиной (код выхода, хвост stderr), остальные шаги `skipped`.
- `backup` с кодом 3 (часть файлов не прочитана) = `warning`, каскад идёт дальше.
- Пропущенные запуски не догоняем (нет `catch-up`).
- Статусы: `queued`, `running`, `success`, `warning`, `failed`, `cancelled`, `skipped`, `interrupted`.
- Отмена: SIGTERM дочернему restic, таймаут (~30 с), потом SIGKILL. При остановке демона: прекратить планирование,
  переслать SIGTERM детям, пометить активные запуски `interrupted`. Stale-lock'и не снимаем автоматически, показываем в статусе.
- restic запускается через `spawn` без shell; секреты через env процесса, не через аргументы; разбор `--json`.
- Для `run`-шагов в дочерний процесс передаётся только заданное в шаге окружение, не всё окружение демона
  (без `PATH` программа ищется в системном пути по умолчанию). `shell: true` = `/bin/sh -c`.
- restic получает окружение демона без `RESTIC_REPOSITORY*`/`RESTIC_PASSWORD*` (и `FROM_`-вариантов), поверх него `env`
  репо (для `copy` сначала источника, потом цели); `options` репо идут как `-o key=value`. Источник для `copy` и
  `init --copy-chunker-params` передаётся через `RESTIC_FROM_REPOSITORY`/`RESTIC_FROM_PASSWORD`.
- Требуется restic >= 0.17 (коды выхода 10 и 12). Любой другой ненулевой код `cat config` = `unreachable`.
- `cat config` ограничен таймаутом (`RESCADE_REPO_CHECK_TIMEOUT`, по умолчанию 2m): недоступный REST/S3 restic
  ретраит минутами. Истёк = `unreachable`, init не делается. У backup/prune/copy/check таймаута нет.
- Коды выхода `rescade run`: 0 success, 3 warning, 1 failed, 130 cancelled, 75 skipped (репо заняты; только через демон),
  2 ошибка использования.

## Инициализация репозиториев и сверка параметров

- Автоинициализация, отдельной команды `init` нет. Перед каждым шагом (внутри мьютекса репо): `restic cat config`.
  Код 10 (репо не существует) → `init` (с `--from-repo` и `--copy-chunker-params`, если задано `from`; источник проверяется первым).
  Неверный пароль или провал `init` → шаг `failed`. Недоступный хост → `unreachable`, `init` не делаем никогда.
- При старте тот же проход как ранний прогрев. Ошибки конфигурации и ошибки на достижимых репо останавливают сервис.
  Во время работы ошибка ensure/init только проваливает шаг.
- Проверка монтирования вне зоны сервиса (в systemd: `RequiresMountsFor=`).
- Сверка `chunker_polynomial` (из `restic cat config`) при старте по рёбрам `from` и перед каждым `copy`.
  Без кеша: репо могли пересоздать вручную. Расхождение = `warning` на шаге, каскад идёт дальше.
  Пересоздание с теми же параметрами не считается ошибкой.

## API и настройки сервиса

- TCP (не Unix-сокет), по умолчанию `127.0.0.1:8765`. Токен обязателен всегда (`Authorization: Bearer`, сравнение за постоянное время).
  Токен через env или файл (права 600), не через аргументы. Проверка заголовка `Host`, CORS только для явно разрешённых origin.
- Настройки сервиса через env/флаги, не YAML: `RESCADE_ADDR`, `RESCADE_URL`, `RESCADE_TOKEN_FILE`, `RESCADE_TOKEN`,
  `RESCADE_CONFIG_DIR`, `RESCADE_DATA_DIR`, срок хранения истории, путь к restic (`RESCADE_RESTIC`),
  таймаут проверки репо (`RESCADE_REPO_CHECK_TIMEOUT`).
- Клиент ищет токен: `--token-file`, `RESCADE_TOKEN`, `RESCADE_TOKEN_FILE`, `~/.config/rescade/token`. Сервер: `/etc/rescade/token`.
  Предупреждение, если права на файл слишком широкие.
- Эндпоинты: `GET /cascades`, `GET /runs`, `GET /runs/:id`, `GET /runs/:id/log?step=`, `POST /cascades/:name/run`,
  `POST /runs/:id/cancel`, `GET /repos`, `GET /events` (SSE). Перезагрузка конфига по SIGHUP.
- Модель данных: run (id, каскад, триггер, статус, времена, причина), step (индекс, тип, статус, код выхода,
  длительность, summary), log (строки по шагам, отдельно от метаданных для ротации). SQLite (`node:sqlite`, WAL,
  версия схемы в `user_version`). Состояние репо и мьютексы в памяти.
- Уведомления отложены (пока статус запрашивается вручную); позже как подписчики на поток событий.

## Тестирование

Фейковый restic-бинарник (скрипт, управляемый переменными окружения): коды 3 и 10, зависание, реакция на SIGTERM.
Это даёт воспроизводимые тесты отмены, warning, ensure/init и блокировок. Плюс отдельный интеграционный прогон
с настоящим restic на локальных репо во временных каталогах.
